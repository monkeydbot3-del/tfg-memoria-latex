\section{Estructura del proyecto}

La aplicación principal se desarrolló en un repositorio independiente del repositorio de la memoria. Su estructura final responde a una organización típica de Flask, ampliada con servicios de autenticación, persistencia y validación técnica.

\begin{verbatim}
/tfg-simulador-inversion
|-- .github/            # Flujos de validacion (GitHub Actions)
|-- app/
|   |-- static/         # CSS, JS e imagenes
|   |-- templates/      # Plantillas HTML (Jinja2)
|   |-- services/       # Servicios de auth, historial y carrera
|   |-- __init__.py     # Factoria de la aplicacion
|   |-- auth.py         # Login, registro, invitado y logout
|   |-- career.py       # Logica del modo carrera
|   |-- db.py           # Inicializacion de base de datos
|   |-- models.py       # Modelos persistentes
|   `-- routes.py       # Rutas principales y API interna
|-- tests/              # Suite de pruebas automatizadas
|-- requirements.txt    # Dependencias del proyecto
`-- run.py              # Punto de entrada
\end{verbatim}

\section{Ramas y versionado}

Durante la fase final del proyecto se utilizaron varias ramas con propósitos diferenciados:

{\sloppy
\begin{itemize}
    \item \texttt{main}: versión principal consolidada del sistema.
    \item \texttt{bot/render-preview}: rama de validación visual en Render durante el rediseño.
    \item \texttt{feature/frontend-redesign-v2}: rama de trabajo del rediseño visual por fases.
    \item \texttt{stable/pre-redesign}: rama de congelación funcional previa al rediseño completo.
\end{itemize}
\par}

Como hito de cierre del rediseño se creó el tag:
\begin{center}
\texttt{v1.1-frontend-redesign}
\end{center}

\section{Instalación y ejecución local}

Para ejecutar el proyecto localmente se requiere Python 3.11 o superior \cite{python}, Git \cite{progit} y un entorno con acceso a las dependencias definidas en \texttt{requirements.txt}.

\begin{enumerate}
    \item \textbf{Clonar el repositorio principal:}
    \begin{verbatim}
    git clone git@github.com:monkeydbot3-del/tfg-simulador-inversion.git
    cd tfg-simulador-inversion
    \end{verbatim}

    \item \textbf{Crear entorno virtual e instalar dependencias:}
    \begin{verbatim}
    python -m venv .venv
    source .venv/bin/activate
    pip install -r requirements.txt
    \end{verbatim}

    \item \textbf{Definir variables de entorno necesarias:}
    \begin{verbatim}
    export SECRET_KEY=...
    export DATABASE_URL=...
    # Opcional:
    export OPENAI_API_KEY=...
    \end{verbatim}

    \item \textbf{Ejecutar la aplicación:}
    \begin{verbatim}
    python run.py
    \end{verbatim}
\end{enumerate}

\section{Despliegue en Render}

El despliegue final se realizó en Render \cite{render}. Durante el desarrollo, la rama de vista previa se utilizó para validar cambios del rediseño sobre el entorno desplegado, mientras que la fase final concluyó con la consolidación del sistema en \texttt{main}. El servicio quedó finalmente alineado con esta rama principal como versión oficial del proyecto.

La aplicación requiere al menos las siguientes variables de entorno:

\begin{itemize}
    \item \texttt{SECRET\_KEY}: clave de sesión de Flask.
    \item \texttt{DATABASE\_URL}: conexión a PostgreSQL.
    \item \texttt{OPENAI\_API\_KEY}: variable opcional para habilitar el Tutor IA.
\end{itemize}

\subsection{Base de datos PostgreSQL}

La persistencia final se apoya en PostgreSQL desplegado también en Render. Durante el cierre del proyecto fue necesario recrear la base de datos tras la expiración de una instancia anterior asociada al plan gratuito. Esta incidencia obligó a revalidar autenticación, historial y navegación en el entorno real.

\section{GitHub Actions y validación continua}

La rama principal quedó respaldada por GitHub Actions, que automatiza la ejecución de validaciones sobre el repositorio y ayuda a detectar regresiones antes de consolidar cambios. Esta integración fue especialmente útil durante el rediseño frontend y en la fase de estabilización final.

\section{Incidencia final de autenticación/navbar}

Una de las últimas correcciones técnicas relevantes consistió en ajustar el renderizado de la barra de navegación tras el inicio de sesión real. Aunque la sesión autenticada existía correctamente, la navbar seguía mostrando acciones propias de usuario anónimo en algunas pantallas internas. La solución consistió en dar prioridad explícita al estado autenticado frente al modo invitado y se reforzó con pruebas automáticas sobre rutas internas.

\chapter{Manual de Usuario}
\label{appendix:manual_usuario}

Este manual resume el flujo funcional final de la aplicación y ayuda a interpretar sus principales pantallas.

\section{Acceso al sistema}

El sistema puede utilizarse de tres formas:
\begin{itemize}
    \item como usuario autenticado;
    \item como usuario invitado;
    \item como visitante que todavía no ha iniciado sesión.
\end{itemize}

El usuario autenticado dispone de persistencia y continuidad. El usuario invitado puede explorar el sistema, pero sin historial persistente entre sesiones.

\section{Modo Práctica}

Permite realizar un análisis puntual de un activo y comparar su evolución con una referencia histórica. Es la forma más directa de comenzar a utilizar la aplicación.

\section{Modo Carrera}

Permite crear sesiones por turnos, configurar carteras y obtener un informe final. Su acceso queda condicionado por el readiness quiz.

\section{Modo Horizonte}

Extiende la experiencia del simulador mediante una proyección experimental basada en patrones históricos. Su uso tiene finalidad educativa y no predictiva.

\section{Tutor IA}

Sobre el informe final del modo carrera puede habilitarse una capa adicional de análisis educativo mediante IA, siempre de forma opcional y condicionada a la variable de entorno correspondiente.
